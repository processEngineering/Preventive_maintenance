Audit date: 2026-10-26
Status: Source audit complete. The isolated self-hosted test package has been run on

SUMMARY
The frontend is directly coupled to Supabase for database reads/writes, authentication
and sessions, profile/role lookups, and public signature-image URLs. A database restore
alone does not replace these services. The detailed source-match inventory is in
mtc-supabase-audit-detail.txt.

APPLICATION DEPENDENCIES

1. Supabase client setup
- A shared client is configured in public/src/supabase/supabase-client.js.
- Checklist pages also initialize their own Supabase clients and load the Supabase JS
  library in the browser. The project URL and client key are therefore frontend-facing.
- Direct client initialization was found in 55 checklist HTML pages.

2. Authentication, sessions, and profiles
- Sign-in uses Auth password login and session checks.
- Registration creates an Auth account, requests email verification with a redirect,
  stores full_name/divisi/jabatan in Auth metadata, and upserts the matching profiles
  row using the Auth user ID. It then signs out.
- Password recovery sends a reset email; the password-update page changes the Auth
  password.
- Application pages check the current Auth session and read profiles for user details
  and role/permission-related behavior. Account pages also support sign-out/profile
  updates.
- Auth behavior to replace: sign-in, registration, email verification, session
  persistence/checks, sign-out, password-reset email, and password update.

3. Database access
- Direct Supabase .from(...) access occurs in 60 source files, including checklist
  entry, approval, result, history, and chart pages, plus authentication, role, and
  account flows.
- Referenced database tables (exact identifiers found in source):
  profiles;
  chslr_items, chslr_log, chslr_mesin, chslr_result;
  clhmi, clhmi_items, clhmi_machine, clhmi_results;
  clpm_items, clpm_log, clpm_result;
  jpdo_approval, jpdo_approval_manager, jpdo_approval_ppc,
  jpdo_approval_produksi, jpdo_log, jpdo_result;
  kartu_riwayat_items;
  Lkmr_result, lkmr_repair;
  pmi_header, pmi_item_fields, pmi_items, pmi_machines, pmi_results;
  pmw_log, pmw_reports;
  pohm_items, pohm_log, pohm_machine;
  ppw_log;
  prslb_items, prslb_log, prslb_mesin, prslb_result.
- Schema check against mtc_migration_test2: all 36 referenced database tables exist
  in public with exact name and capitalization. Lkmr_result is mixed-case in both
  source and database.
- The profiles table has 22 rows. Its columns are id (UUID primary key),
  full_name, divisi, jabatan, and created_at; it contains no email column.
- An aggregate check in the Supabase project confirmed 22 profiles, 22 matching Auth
  user IDs, and 22 matching accounts with email addresses. This confirms the profile
  IDs can be preserved; the private email-to-ID list must remain with the authorized
  administrator and must not be pasted into chat or committed.
- The schema comparison initially included "signatures" as a presumed table, but
  source inspection confirms its .from('signatures') calls are Storage bucket calls,
  not database-table queries. No missing database table was identified.

4. Supabase Storage
- CHSLR and CLHMI result pages call getPublicUrl() for objects in the "signatures"
  bucket and display those images.
- CHSLR coordinator, pelaksana, and superintendent flows upload new signature PNGs
  to that bucket; result pages read public URLs.
- The source audit cannot confirm whether the bucket contains required files, its
  access policy, or whether referenced paths are stored as object keys or URLs.

5. Other Supabase features
- No RPC, Realtime channel, or Supabase Functions calls were found in the searched
  application source.

REPLACEMENT-BACKEND IMPLICATIONS
- The API must cover the table reads/writes and workflow transitions used by the
  checklist, approval, result, history, chart, and profile flows.
- The backend must replace Supabase Auth and enforce identity, session expiry, and
  role/permission checks server-side; frontend-only gating is not a substitute.
- Email verification and password recovery need an explicit replacement flow.
- Signature images need a planned storage location and access strategy, including
  validating whether the existing Supabase bucket contains files still in use.
